# Core: *Threadbare* -- Full Curriculum (English)

Extracted 4 August 2026 from the English source decks in Google Drive. Five milestones spanning 18 sessions, plus the learner playbook.

**Program shape:** a cohort course. Learners build a StoryQuest across five milestones; the deliverable is a playable prototype published from their own GitHub organization.

**Fidelity note and a real warning about coverage:** Milestones 4 and 5 and the Learner Playbook extracted richly -- the playbook in particular carries the full project board with per-task acceptance criteria for all five milestones, a roughly 100-term glossary, and the complete GitHub setup walkthrough. Milestones 1 through 3 are much thinner, because those decks are visually driven: most session slides carry only an activity title, with the instruction living in embedded visuals, videos, or linked worksheets that text extraction cannot reach. Treat the Milestone 1-3 sections as a reliable skeleton, not as complete teaching content. There is no scored rubric and no standalone code of conduct in any source; assessment is the acceptance-criteria checklists.

#### Open Source

*Threadbare* is open source! This means that we are in front of a development model where software source code is made publicly available, allowing anyone to use, modify, and distribute it freely. And this implies:

- Code and assets are public and openly-licensed
- The game "lives" in Github, where all of this plus issues and pull requests are also visible and can be tracked
- When you contribute to *Threadbare*, your work lives on! Even after the program, you can keep working on your StoryQuest, propose another, or even contribute to other parts of the *Threadbare* game (either independently or in other programs, like More).

#### Core: Learning Principles

**Everyone belongs.**
We celebrate inclusion and diversity within the game-making community.

**Play matters.**
We recognize creative play as fundamental to learning and living.

**Create for impact.**
We inspire game makers who create meaningful change in the world.

**Share often. Be open.**
We promote safe, collaborative spaces where game makers learn from one another.

**Reflect and refine.**
We value intentional reflection that helps us grow and evolve.

**Learning is not linear.**
We embrace flexibility and failing forward in an iterative design process.

#### Core: Learner Outcomes

By the end of this program, you will:

- Understand key game design concepts
- Come up with ideas for a StoryQuest
- Create a prototype of a playable StoryQuest\*
- Plan a game design project
- Collaborate with others to build your game
- Consider the diverse needs of players
- Communicate your game idea\* to others

\*how you will be assessed

### Session 4.1 (Session 14) -- What makes a StoryQuest good?

#### Title slide

**What makes a StoryQuest good?**

> Facilitator note: **Overview**
>
> This is the first session of a new Milestone: #4, Playtesting and Iteration. This session and the ones that follow focus on sharing prototypes with "the outside world," so [playtesting sessions](https://github.com/StoryQuest-Project-Board/threadbare/issues/23) will be held to collect information, in order to later on polish the StoryQuests. The first step in sharing the prototypes will be making playable links for each fork available, so on the [Endless Studios platform](https://studio.endlessstudios.com/studio/), each team can create a web page for their project. This way, they'll be able to share their work with classmates. The second step is to take the prototype even further -- sharing it with friends, family members, and others, using more targeted feedback forms.
>
> "Outsider" input provides a fresh perspective: because they are not involved in the games' creation, playtesters can easily identify bugs and inconsistencies in addition to other potential improvements. For example, if team makes a StoryQuest about climate change, questions for playtesters might include: Does the game convey awareness about climate change? In what way? Are you more interested in learning about climate change after playing? Game makers can refine their work based on the answers they receive during playtesting.

> Facilitator note: **Preparation**
>
> In this session, game makers will follow the Project Board issue [Conduct playtesting sessions](https://github.com/StoryQuest-Project-Board/threadbare/issues/23) (there they will also find the tutorial [Enable playable links for a Threadbare fork](https://github.com/endlessm/threadbare/discussions/1123), which was already proposed in Milestone 3 and is essential for these playtesting stages).
>
> This is a good moment to reflect: Is there a defined target audience? Can the developers reach out to classmates, friends, family members, or other people who fit into the chosen audience category? And what if there isn't a defined target audience and anyone could play and enjoy the StoryQuest? That scenario might actually be an even better opportunity to gather data on how the prototype works. Taking note of first impressions, bugs, and other feedback will help improve both the overall goal of the StoryQuest and each of its mini-games.
>
> As always, please set up any online tools needed, such as breakout rooms, online whiteboards, and digital sticky notes. For in-person settings, prepare materials like posters, sticky notes, and pens. Test all technical equipment in advance to ensure everything is running correctly and that you have smooth video playback and interaction on the session slides.

#### Opening Question: Have you shared your StoryQuest with others? -- 5 min

**Have you shared your StoryQuest with others?**

> Facilitator note:
> - Welcome game makers and ask them the opening question: "Have you shared your StoryQuest with others?"
> - Encourage game makers to answer the question even if the answer is "no". Ask follow up questions with an open mind: for ex., if they were insecure about sharing their prototype with someone because they knew there was still a lot to polish, share with them the value of playtests at any stage of game development. A fresh perspective catch things that the developers cannot (because they are too close to the work), and it also allows game makers to test the target audience (if it was taken into consideration when planning).
>
> For online environments: Encourage game makers to turn on their cameras. They can use the raise hand feature or respond in chat.
>
> Time Saving Tip [for in-person settings]: To avoid a long, whole-group discussion, participants can share their answers with a peer near them.

**Plan a playtesting session**

### An Overview of Core: Threadbare

In this guide, you will learn how to craft original adventures in the whimsical, worn world of *Threadbare* - a journey of restoration where stories weave the fabric of a forgotten world back together.

Long ago, the First Storyweaver spun the Sacred Elements - Memory, Imagination, and Spirit - into threads and wove them on the Eternal Loom, creating the Weave, the living fabric of reality. But now the world is unraveling. The Eternal Loom lies dormant at Fray's End, and the last Elders cling to fading tales. Dark forces -- Ink Drinkers, Memory Miners, and Spirit Stealers -- roam the lands, devouring the essence of culture, identity, and language.

You are a newly summoned Storyweaver, heir to the First Storytellers, called to reclaim lost stories and restore the Weave. Through StoryQuests -- interactive journeys of your own making -- you'll design characters, shape meaningful choices, and build imaginative encounters that invite others into the world of *Threadbare*.

Whether you're a solo storyteller, a family of adventurers, or a creative team, this guide will help you bring new stories to life - thread by thread. Learn more in these [video playthroughs](https://drive.google.com/drive/folders/1j_25kWZxfnoxOG7wyjuZb-EyFhNV7ckf?usp=sharing)!

### Requirements

This program requires the following materials and resources:

**Technology**

- A computer (Windows, macOS, or Linux) connected to the Internet
- Godot Engine (free and open source) - download from godotengine.org
- A Google account (for copying and editing planning documents)
- A GitHub account (for uploading and contributing your StoryQuest to the community game!)
- Optional: A Studio account (for connecting with our game-making community, earning skill achievements, and building your portfolio)

**Skills/Knowledge**

- Basic familiarity with digital tools, file system structures, and coding concepts
- Understanding of story structure (beginning, middle, end)

### Learning Principles

**Everyone belongs.** We celebrate inclusion and diversity within the game-making community.

**Play matters.** We recognize creative play as fundamental to learning and living.

**Create for impact.** We inspire game makers who create meaningful change in the world.

**Share often. Be open.** We promote safe, collaborative spaces where game makers learn from one another.

**Reflect and refine.** We value intentional reflection that helps us grow and evolve.

**Learning is not linear.** We embrace flexibility and failing forward in an iterative design process.

### Our Learning Approach

In this program, we follow a simple but powerful approach to learning and making games: Play, Create, Share, and Reflect.

**Play** means exploring and enjoying existing games to understand what makes them fun and meaningful.

**Create** is where you bring your own ideas to life by designing and building your StoryQuest.

**Share** invites you to show your game to others, give and receive feedback, and learn from each other.

**Reflect** encourages you to think about what worked well, what could be better, and how your story or game can grow.

This way of learning helps you dive right in -- learning by doing, experimenting, and collaborating. It's a hands-on approach that builds skills like creativity, problem-solving, and teamwork, while making the process fun and engaging. As you work through your StoryQuest, you'll experience all four steps again and again, helping you become a confident and thoughtful Storyweaver, ready to craft meaningful stories that connect with others.

### Let's Get Started!

#### Becoming Your Own StoryQuest Studio Lead

Welcome to your StoryQuest journey! In this section, you'll learn how to set up your own game development workspace using GitHub. Normally, mentors or instructors do this part -- but in a self-guided learning environment, **you** get to be the Studio Lead! This means you'll:

- Create a digital workspace using GitHub (called an "Organization")
- Fork the *Threadbare* game template so you can build your own StoryQuest
- Manage your game project like a pro!

Whether you're working solo, with friends, or as a family, these steps will help you get started.

#### Why Use a GitHub Organization?

A GitHub Organization keeps everything neat and in one place:

- Your game files, project plan, and updates live in one tidy hub
- You (and your teammates, if any) can see and edit your shared game project
- You learn real-world skills by working in the same way professional developers do

Even if you're working alone, it's worth it.

#### What You'll Need

- A GitHub account: [Create one here](https://github.com/join)
- Basic computer skills (copy/paste, using a web browser)
- 20-30 minutes of setup time

**1. Create a GitHub Organization**

1. Sign in to GitHub.

4. Name your organization something like Threadbare-Studio-YourStudioName or StoryQuest-Team-A.
5. Use your email as the contact email. Select "Personal" as the organization type.
6. Complete the image puzzle or identity verification, if prompted.

**2. Skip Inviting Users (for now)**

**3. Install the Threadbare StoryQuest Setup App**

This app will help fork the main game and create your project board.

- Go to the [Threadbare StoryQuest Setup app](https://github.com/apps/threadbare-storyquest-setup)
- Click **Install** → Select your new organization
  - **DO NOT** install it in your personal account. Use the new org you made in Step 1.
- Confirm password or 2FA if prompted

**4. Wait for Your Project Board to be Created**

**Before moving on to the next step,** you must wait for your threadbare fork & project board to be created. ### Appendix - Glossary

**A**

**Abilities -** The actions or powers a character can use in a game, such as jumping, dashing, or casting a spell. Abilities often define the player's options and can grow or change through skill trees or upgrades.

**Aesthetics -** The visual and artistic aspects of a game, including colors, character design, and environmental elements that contribute to the player's experience.

**Ambient -** Background sounds or music that help create the atmosphere of a game's world and make spaces feel more alive.

**Art -** A domain of game making that involves the visual and audio components of a game, including character design, environmental assets, sound design, UI elements, and animations.

**Assessment -** Methods used to evaluate learners' progress, including informal reflection and formal rubrics.

**Asset (Game Asset) -** Any visual, audio, or interactive element used in a game, such as characters, backgrounds, music, sound effects, or animations.

**B**

**Backlog -** The list of things that still need to be added, fixed, or improved in a game.

**Branch -** A version of a project where changes can be made without affecting the main branch. Branches allow game makers to experiment or add features safely.

**C**

**Cell shading -** A visual style that uses bold outlines and flat colors to make 2D or pixel art stand out with a clear, high-contrast look.

**Cloning -** The process of creating a local copy of a repository from a remote server, such as GitHub.

**Collaboration -** The process of working together to design, create, and refine game projects, often involving feedback and playtesting.

**Commit -** A save point in Git that records the changes you selected. Commits create a history of your project that you can go back to if needed.

**Compliment, Coach, and Encourage -** A feedback approach that focuses on highlighting strengths, offering guidance for improvement, and motivating learners to keep progressing.

**Contribution -** A change, feature, or asset added to a shared project.

**Constant -** A value in programming that does not change while the game is running, often used for settings like speed or gravity.

**Core Gameplay Loop -** The repeated cycle of player actions, rewards, and challenges that keep the game engaging.

**Creative Agency -** The ability of learners to take ownership of their projects and make independent creative decisions.

**D**

**Decomposition (Problem Decomposition) -** The process of breaking down complex game design tasks into smaller, manageable parts.

**Deliverables -** Tangible outcomes expected from learners, such as a playable game and a game pitch presentation.

**Diversity & Inclusivity -** Ensuring that games represent and are accessible to players from a variety of backgrounds and experiences.

**Domain -** A specific area of expertise within game development that focuses on a distinct aspect of the creation process (Engineering, Marketing, Game Design, Art, and Management and Production).

**E**

**Engagement -** The level of involvement and interaction learners have with the game-making process.

**Engineering -** A domain of game making that involves the technical aspects of game development, including programming, physics simulation, and system architecture using the Godot engine.

**Experiential Learning -** Learning through hands-on activities, exploration, and iteration rather than passive instruction.

**F**

**Feedback -** Constructive critique provided by peers, instructors, or mentors to help refine game designs.

**Feature Branch -** A branch created to work on a specific feature or change in a project. It can later be merged back into the main branch after review.

**Fork -** A copy of a repository created under your own GitHub account, allowing you to make changes freely without affecting the original project.

**Frame Drops -** Games are made up of many images, called frames, shown very quickly to create motion. Frame drops happen when the game can't show these images fast enough, causing movement to look choppy or stutter. This can make the game feel less smooth or harder to control.

**Function -** A reusable block of code that performs a specific task, such as moving a player or playing a sound.

**Future-Ready Skills -** Essential competencies such as problem-solving, collaboration, and adaptability that prepare learners for careers in and beyond game development.

**G**

**Game -** An interactive experience designed to engage players through challenges, choices, and feedback, often providing entertainment, education, or storytelling.

**Game Design -** A domain of game making that involves the creative process of designing gameplay mechanics, player interactions, level structures, and overall game flow.

**Game Design Document (GDD) -** A structured outline that details the concept, mechanics, story, and visuals of a game.

**Game Design Journal -** A personal record where game makers capture ideas, plans, reflections, and progress throughout the design process.

**Game Engine -** A software framework used to develop video games, providing essential tools for rendering graphics, handling physics, scripting gameplay mechanics, and managing assets.

**Game Elements -** The basic building blocks of a game, such as rules, goals, challenges, mechanics, and space.

**Game Maker -** A learner or creator engaged in designing, developing, and refining video games, applying principles of game design, mechanics, storytelling, and user experience.

**Gameplay Mechanics -** The rules and actions that define how players interact with the game world, such as jumping, collecting, or solving puzzles.

**Game Systems -** The interconnected rules, mechanics, and processes that make a game function, such as scoring, health, physics, or inventory. Together, they shape how the game responds to the player's actions.

**Git -** A version control system used to track changes in code, manage different project versions, and collaborate with others (eg, GitHub).

**Git Bash (Terminal/Command Line) -** A text-based interface where Git commands are typed to interact with a repository, such as creating branches or committing changes.

**Git Command -** An instruction typed into the terminal to tell Git what to do, such as git status to see the state of your project.

**Glitch -** An unexpected error or bug in a game that causes it to behave in ways the designer didn't intend.

**Go-To-Market -** A domain of game making that involves the strategies for launching a game, including audience research, marketing, distribution, and community engagement.

**Godot Engine -** A free and open-source game engine used for designing and developing games in the Core: Godot program.

**Grayboxing -** A level design method where simple shapes and placeholder objects are used to plan a game's layout and gameplay before adding final art or details.

**I**

**Immersion -** The feeling of being deeply involved in a game world, often created through visuals, sound, story, and smooth gameplay.

**Iteration -** The process of refining a game through repeated cycles of prototyping, playtesting, and feedback.

**L**

**Lag -** A delay between a player's input and the game's response, often caused by network or performance issues.

**Learner Outcomes -** The knowledge and skills learners are expected to gain by completing the program, such as understanding game mechanics and creating a playable game.

**Level -** A distinct section of a game, designed with specific challenges, objectives, and environments.

**Level Design -** The process of designing and structuring the spaces within a game, ensuring progression, challenges, and engagement.

**Level Design Document -** A plan that outlines a level's layout, goals, mechanics, and flow before it is built in the game engine.

**Local Repository -** The version of a Git project stored on your own computer, where you make and save changes before sharing them online.

**M**

**Management & Production -** A domain of game making that involves the process of organizing and leading a game development project, including teamwork, workflow management, and iterative development.

**Main Branch -** The central branch of a project that represents the official version of the game. Finished and reviewed changes from feature branches are merged here.

**Mechanics -** The rules and systems that define how a game functions and how players interact with it.

**Mentors -** Industry professionals who provide guidance, insights, and feedback to learners throughout the game-making process.

**Merge -** The process of integrating changes from one branch into another in an open-source project.

**Merge Conflict -** When branches are merged, Git attempts to combine their changes into a single branch. Conflicts may arise if the changes affect the same parts of a file, requiring manual resolution before the merge can be completed.

**Moodboard -** A collection of pictures, colors, and words that show how a video game idea should look and feel.

**Modding -** Modifying an existing game to experiment with game mechanics, aesthetics, and player experiences.

**N**

**Narrative -** In video games is the story of the game. It tells who the characters are, what is happening, and why the player goes on the adventure.

**O**

**Open Source -** Software with a publicly accessible source code that can be freely used, modified, and shared by anyone, often developed collaboratively by a community of contributors.

**Optimization -** The process of improving how efficiently a game runs by reducing lag, shortening load times, and making assets or code perform better.

**P**

**Pedagogy (Play, Create, Share, Reflect) -** The learning approach used in the Core: Godot program, emphasizing hands-on creation, collaboration, and iterative improvement.

**Pitch -** A short presentation of a game idea used to share its concept, goals, and appeal with others.

**Pixel Art -** A digital art style where images are created with visible square pixels, often used in retro or stylized games.

**Platformer -** A type of game where players jump, run, and navigate across platforms or obstacles, often focusing on timing, precision, and movement through levels.

**Player -** An individual who interacts with a game, engaging with its mechanics, challenges, and narrative to achieve objectives or explore its world.

**Player Character (PC) -** The character you control in a game. It's the one you move, jump, and use to play the game.

**Playtest -** The process of testing a game with players to gather feedback and improve gameplay.

**Problem Decomposition -** The process of breaking down complex game design tasks into smaller, manageable parts.

**Prototyping -** Creating an early version of a game to explore mechanics and test ideas before finalizing the design.

**Pull (Git) -** The action of bringing the latest commits from a remote repository (like GitHub) into your local repository to update your project.

**Pull Request (PR) -** A request to merge changes from one branch or fork into another. Pull requests let others review, discuss, and approve your changes before they become part of the main project.

**Push (Git) -** The action of sending your commits from your local repository to a remote repository (like GitHub) so that others can see your changes.

**R**

**Remote Repository -** The version of a Git project stored online (for example, on GitHub) that allows you to back up your work and collaborate with others.

**Repository -** A project folder tracked by Git that contains all of the files, history, and branches for a game or program.

**S**

**Scaffolding -** Providing structured support to help learners develop skills progressively before working independently.

**Scope -** The overall size and complexity of a game project, including how much content, art, and gameplay it will include. Managing scope helps keep a project realistic and achievable.

**Session Structure -** The organization of each learning session, including essential questions, activities, and assessments.

**Side Quests -** Supplementary learning activities that allow learners to explore specific topics in game design at their own pace.

**Skill Tree -** A visual system that shows how a player's abilities or powers can grow and branch over time. Unlocking new skills often depends on choices or progress made earlier in the game.

**Spawner -** A node or script in a game that automatically creates or "spawns" objects, enemies, or items at certain times or locations.

**Sprite -** A 2D image or animation used to represent a character, object, or other visual element in a game.

**Sprite frames -** The individual images that make up a sprite's animation sequence, shown in order to create movement.

**Staging -** The step in Git where you pick and choose which files or changes to prepare for the next commit, like selecting which edits in your game you want to save.

**Storyboard -** A sequence of drawings or panels that show how the player will experience key moments, actions, or cutscenes in the game.

**Stuttering -** Brief pauses or uneven motion in a game caused by performance issues, often related to frame drops or loading.

**Systems Thinking -** Understanding how different elements in a game interact and influence each other.

**T**

**Technical Skills -** Skills related to coding, using game engines, designing UI, and implementing sound and animations in a game.

**TileMap -** A grid-based system in Godot used for designing and organizing game environments.

**U**

**Untracked Files -** Files that exist in your game project but are not yet being tracked by Git. Git only saves them once you add and commit them.

**User Experience (UX) -** The overall feel and accessibility of a game from the player's perspective.

**User Interface (UI) -** The visual elements of a game, such as menus, buttons, and HUDs, that allow players to interact with the game.

**V**

**Version Control System (VCS) -** A tool that tracks changes to files and projects over time, letting multiple people collaborate and return to earlier versions if needed.
